# Logins worker setup and acceptance

Logins requires two separate standard Windows identities: one for every ordinary provider/Full auto launch, and one used only by the trusted project-review flow. The native vault entry window, secret store and browser fill remain with the owner. Full auto retains automatic execution within assigned bot/project folders without receiving the owner's identity or the review account's Windows logon credential, writable profile or policy registry. Other software already running as the owner or an administrator remains outside this protection. A receiving website can expose a submitted value.

Setup changes local accounts and ACLs. Review these artifacts and obtain the owner's approval before executing them. Close Tjommie first. In an elevated PowerShell window **as the same Windows owner**, run:

```powershell
& 'C:\Users\OWNER\AppData\Local\Programs\Tjommie\resources\daemon\tjommie-daemon.exe' provision
```

`provision` is the Rust daemon's replacement for `provision-worker.ps1` (which stays in this folder). It prints which data root it is setting up (`TJOMMIE_HOME`, else `%LOCALAPPDATA%\Tjommie`) before it creates anything, refuses a root that already has the worker configurations, and undoes what it did if anything fails. It creates a provider account named `TjWorker-<namespace>` and a review account named `TjReview-<namespace>`. It protects the data root, stores two independent random Windows logon credentials directly in the owner's namespaced Credential Manager entries, and writes `worker.json`, `review-worker.json` and a persistent `vault-protection-required` marker. It does not read existing credentials, copy CLI authentication, install a service, change autostart or restart Windows. The desktop application continues to run unelevated. Preserve the protection marker if configuration breaks; losing either configuration must not restore owner-level provider execution.

Install the supported Windows Node executable and both provider CLI distributions beneath the printed protected `runtime` folder. Keep `node.exe` directly in that folder. Native `claude.exe`/`codex.exe` may be directly in it or in matching `claude`/`codex` subfolders; npm distributions may use its `node_modules` folder. Install as the owner so both worker identities have read/execute access and cannot replace runtime code. Before every readiness/launch check, the helper verifies the entire runtime tree, including each file's owner and explicit/inherited ACL. It rejects links, null DACLs and any untrusted write/delete/ACL-changing right. A protected root does not excuse a writable child. The bounded audit refuses trees exceeding 100,000 nodes or 20 seconds; native CLI distributions keep this closure small. Do not copy owner CLI profiles or authentication. No global package installation is required by Tjommie.

Every launch uses a short fixed program in the protected `node.exe`, including launches of native provider executables. This keeps the Windows logon API command within its 1,024-character limit. The target executable and arguments travel in a bounded private stdin frame, followed by the provider's unchanged input bytes. No launch payload is stored on disk or in bootstrap arguments/environment; the Windows logon password is never in that frame. The target retains inherited stdin/stdout/stderr, cwd and the validated environment. Node startup variables (`NODE_*` and `ELECTRON_RUN_AS_NODE`, ignoring case) are removed for both bootstrap and target. NUL environment entries/arguments are refused before native preparation. Rendered target command lines may use the normal Windows limit of 32,767 UTF-16 code units including the final terminator; longer commands fail before any account launch.

The suspended bootstrap's SID/token is verified and assigned to an owner/System/Administrators-only named Job before resume. Its provider children inherit that Job. Native v3 launch receipts bind the Job name, purpose, SID and root process; both configuration and durable acceptance receipts remain v2. Other running CLI candidates are exempted only with live pinned process handles and kernel-confirmed membership in those protected Jobs. A PID list or parent relationship is insufficient. Paired status checks and process preparation share a short serialized gate until the native receipt is registered. A confirmed retirement permits one fresh attempt if an earlier Job disappeared during preparation. Unknown retirement blocks queued and held preparation, preserves reservations and requires reconciliation.

Restart Windows after provisioning. Readiness refuses a boot predating provisioning. Close older Tjommie/provider apps and disable their automatic startup before acceptance: readiness also rejects owner-level Claude/Codex processes and untracked worker provider processes. Restarting alone does not prove exclusivity if an older app starts again. These scripts do not stop apps or change their startup settings.

Before reopening Tjommie, run the acceptance check. Open a normal (not elevated) PowerShell window as the same Windows owner, make sure Tjommie and any Claude or Codex app are closed, and run:

```powershell
& 'C:\Users\OWNER\AppData\Local\Programs\Tjommie\resources\daemon\tjommie-daemon.exe' accept-worker
```

`accept-worker` is the Rust daemon's replacement for `accept-worker.ts` (the TypeScript runner of 0.4.2, which stays on the `legacy` branch). It is a subcommand of the shipped daemon, so nothing else is installed or packaged for it. Like `provision`, it prints which data root it is checking (`TJOMMIE_HOME`, else `%LOCALAPPDATA%\Tjommie`) before it creates anything. It first runs the daemon's own readiness check on both identities, so a refusal says why (a restart is due, a Claude or Codex process is still running, a runtime file is writable). It then creates one unique synthetic owner marker and one synthetic namespaced owner credential. It launches fixed disposable fixtures under both identities (the protected runtime's `node.exe` runs them: it is the only program a worker may start) and requires denied owner file/credential/process/interactive-desktop access, permitted own-folder writes, and denied peer file reads/writes, policy-registry modification and process-memory access. Each peer fixture is demonstrably live and has created its known marker/key before the denial probe runs. It runs both real CLIs with `--version` under both identities and observes the actual review SID's policy before and after its scoped work. No model turn or owner credential enumeration/read occurs.

The check fails closed. Both receipts are removed before anything runs (an old receipt that cannot be removed stops the run), written only after every check of both identities held, taken back if Tjommie's own readiness check does not accept the pair, and removed again if any check fails or errors, so a failed run never leaves the isolated worker mode looking accepted. A failure exits with an error that names what did not hold. If a worker process tree cannot be confirmed stopped, its `acceptance-<id>` scratch folders stay under the worker roots for reconciliation; delete them only once no process of either worker account is running. Everything else the check made (the synthetic credential and marker) is removed either way.

Acceptance writes `worker-acceptance.json` and `review-worker-acceptance.json` only after all checks pass. Each receipt binds its purpose, both SIDs and both exact configuration hashes, in the byte format 0.4.2 wrote and accepts. Startup requires both receipts and native verification; an old single-account receipt cannot enable the feature. Source tests and successful compilation are not a substitute for this machine acceptance: the Rust check's protocol, receipt bytes and probe programs are unit-tested, the whole harness runs over a fake Windows in tests, and an administrator-only test exercises two real disposable accounts, but no workflow runs it automatically (the opt-in `Worker acceptance (admin, disposable runner)` workflow, `.github/workflows/worker-acceptance-admin.yml`, runs it on demand), and the check has not yet been run against real worker accounts on the owner's PC.

Reopen Tjommie. Sign in separately to the fresh provider-owned profiles through Accounts. Existing owner profiles remain in place and are not copied or used. Project review resolves its scratch/configuration folders under the separate review root before starting any CLI. The same selected provider API account/key may be used according to existing account reservations and budgets; the separation protects the Windows logon credentials, profiles and registry, not ownership of that chosen provider API account.

Review launches require a private review-only lifetime lease. Only the trusted version/acceptance/review and fixed policy-observer flow can use it; ordinary setup, provider turns and project checks remain on the provider identity. A late callback retaining an expired scope is refused. The native wrapper also holds an owner/System/Administrators-only global mutex keyed to the review SID, excluding another host or acceptance fixture throughout each native job. It durably creates an owner-protected active marker before creating a process and removes it only after confirmed job retirement. A stale marker or abandoned mutex refuses reuse, even if the old OS mutex has disappeared; reconcile the owned job rather than delete that marker to bypass it. Serialized review launches wait for native job retirement, and matching policy observations are required before and after the flow. Unknown termination retains the lease, marker and account reservation. Full auto cannot mutate that review SID's policy/profile while it runs. This arrangement does not require global cross-user WTS ownership enumeration or an elevated desktop application.

Provider directory grants preserve assigned `bots/<id>` and `workspaces/<id>` paths plus explicitly selected external projects. They refuse owner metadata/account/log/attachment/configuration/receipt paths, either peer root or actual peer OS profile, and trusted runtime/helper ancestors and descendants. Junction targets are canonicalized; the native ACL update pins and verifies the directory handle before modifying that same handle. The review identity accepts cwd/profile grants only within its own root.

Host-native Logins unlock/save/fill controls become available only while the daemon supplies an authenticated live isolation lease. Closing, restarting or disconnecting the daemon locks Logins; restart always starts locked. Clearing private fields leaves browser automation paused until the person explicitly returns control. Closing a private browser retains its profile and sign-ins. The hidden synthetic HTTPS source probe proves the fill/privacy seams separately from these Windows SID/store checks.

To remove setup, first delete all Logins entries in Tjommie and resolve pending deletions. Lock and close Tjommie. Have the owner remove both named standard accounts and their exact namespaced Windows logon credential entries, then review the worker folders and protection marker. Do not delete browser profiles or owner account data during worker removal. Automated removal is omitted until an exact empty-vault/owned-process teardown receipt is available.
