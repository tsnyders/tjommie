# Logins worker setup and acceptance

Logins requires two separate standard Windows identities: one for every ordinary provider/Full auto launch, and one used only by the trusted project-review flow. The native vault entry window, secret store and browser fill remain with the owner. Full auto retains automatic execution within assigned bot/project folders without receiving the owner's identity or the review account's Windows logon credential, writable profile or policy registry. Other software already running as the owner or an administrator remains outside this protection. A receiving website can expose a submitted value.

Setup changes local accounts and ACLs. Review these artifacts and obtain the owner's approval before executing them. Close Tjommie first. In an elevated PowerShell window **as the same Windows owner**, run:

```powershell
& .\provision-worker.ps1 -OwnerDataRoot 'C:\Users\OWNER\AppData\Local\Tjommie'
```

The script creates a provider account named `TjWorker-<namespace>` and a review account named `TjReview-<namespace>`. It protects the data root, stores two independent random Windows logon credentials directly in the owner's namespaced Credential Manager entries, and writes `worker.json`, `review-worker.json` and a persistent `vault-protection-required` marker. It does not read existing credentials, copy CLI authentication, install a service, change autostart or restart Windows. The desktop application continues to run unelevated. Preserve the protection marker if configuration breaks; losing either configuration must not restore owner-level provider execution.

Install the supported Windows Node executable and both provider CLI distributions beneath the printed protected `runtime` folder. Keep `node.exe` directly in that folder. Native `claude.exe`/`codex.exe` may be directly in it or in matching `claude`/`codex` subfolders; npm distributions may use its `node_modules` folder. Install as the owner so both worker identities have read/execute access and cannot replace runtime code. Before every readiness/launch check, the helper verifies the entire runtime tree, including each file's owner and explicit/inherited ACL. It rejects links, null DACLs and any untrusted write/delete/ACL-changing right. A protected root does not excuse a writable child. The bounded audit refuses trees exceeding 100,000 nodes or 20 seconds; native CLI distributions keep this closure small. Do not copy owner CLI profiles or authentication. No global package installation is required by Tjommie.

Restart Windows after provisioning. Readiness refuses a boot predating provisioning. Close older Tjommie/provider apps and disable their automatic startup before acceptance: readiness also rejects owner-level Claude/Codex processes and untracked worker provider processes. Restarting alone does not prove exclusivity if an older app starts again. These scripts do not stop apps or change their startup settings. Before reopening Tjommie, run:

```powershell
& 'C:\ProgramData\Tjommie\Worker-NAMESPACE\runtime\node.exe' .\acceptance\main.mjs 'C:\Users\OWNER\AppData\Local\Tjommie' '..\daemon\windows-worker.ps1'
```

From a source checkout, `node scripts/vault/accept-worker.ts <dataRoot>` runs the same acceptance source. It creates one unique synthetic owner marker and one synthetic namespaced owner credential. It launches fixed disposable fixtures under both identities and requires denied owner file/credential/process/interactive-desktop access, permitted own-folder writes, and denied peer file reads/writes, policy-registry modification and process-memory access. Each peer fixture is demonstrably live and has created its known marker/key before the denial probe runs. It runs both real CLIs with `--version` under both identities and observes the actual review SID's policy before and after its scoped work. No model turn or owner credential enumeration/read occurs. Unknown process-tree termination retains scratch folders for reconciliation.

Acceptance writes `worker-acceptance.json` and `review-worker-acceptance.json` only after all checks pass. Each receipt binds its purpose, both SIDs and both exact configuration hashes. Startup requires both receipts and native verification; an old single-account receipt cannot enable the feature. Source tests and successful compilation are not a substitute for this machine acceptance. It has not been executed on the development host.

Reopen Tjommie. Sign in separately to the fresh provider-owned profiles through Accounts. Existing owner profiles remain in place and are not copied or used. Project review resolves its scratch/configuration folders under the separate review root before starting any CLI. The same selected provider API account/key may be used according to existing account reservations and budgets; the separation protects the Windows logon credentials, profiles and registry, not ownership of that chosen provider API account.

Review launches require a private review-only lifetime lease. Only the trusted version/acceptance/review and fixed policy-observer flow can use it; ordinary setup, provider turns and project checks remain on the provider identity. A late callback retaining an expired scope is refused. The native wrapper also holds an owner/System/Administrators-only global mutex keyed to the review SID, excluding another host or acceptance fixture throughout each native job. It durably creates an owner-protected active marker before creating a process and removes it only after confirmed job retirement. A stale marker or abandoned mutex refuses reuse, even if the old OS mutex has disappeared; reconcile the owned job rather than delete that marker to bypass it. Serialized review launches wait for native job retirement, and matching policy observations are required before and after the flow. Unknown termination retains the lease, marker and account reservation. Full auto cannot mutate that review SID's policy/profile while it runs. This arrangement does not require global cross-user WTS ownership enumeration or an elevated desktop application.

Provider directory grants preserve assigned `bots/<id>` and `workspaces/<id>` paths plus explicitly selected external projects. They refuse owner metadata/account/log/attachment/configuration/receipt paths, either peer root or actual peer OS profile, and trusted runtime/helper ancestors and descendants. Junction targets are canonicalized; the native ACL update pins and verifies the directory handle before modifying that same handle. The review identity accepts cwd/profile grants only within its own root.

Host-native Logins unlock/save/fill controls become available only while the daemon supplies an authenticated live isolation lease. Closing, restarting or disconnecting the daemon locks Logins; restart always starts locked. Clearing private fields leaves browser automation paused until the person explicitly returns control. Closing a private browser retains its profile and sign-ins. The hidden synthetic HTTPS source probe proves the fill/privacy seams separately from these Windows SID/store checks.

To remove setup, first delete all Logins entries in Tjommie and resolve pending deletions. Lock and close Tjommie. Have the owner remove both named standard accounts and their exact namespaced Windows logon credential entries, then review the worker folders and protection marker. Do not delete browser profiles or owner account data during worker removal. Automated removal is omitted until an exact empty-vault/owned-process teardown receipt is available.
