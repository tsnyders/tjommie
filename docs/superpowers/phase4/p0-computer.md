## Source evidence and missing behavior

`packages/daemon/src/native-browser-handlers.ts` returns `frame: null` and refuses `browser.input`. Resize is state-only on this native path. UI `BrowserPanel` and `nativeBrowserAvailable` require the local native desktop bridge. Existing browser schema/frame code does not establish working native remote control.

`NativeBrowserEngine.#present` hides native child surfaces unless mounted in a visible owner window. The failed hidden-capture probe is a concrete reason to resolve painting/capture behavior before relying on that engine for a tray-hidden host, remote viewport or thumbnails. It is not evidence that capture fails in all environments or visible native views.

Browser control is currently a global human/bot flag, not an authenticated per-device controller lease. `withAutomation` checks it before dispatch, and queued jobs use the engine's tail. That alone does not revoke all in-flight JavaScript, create a private vault state, or establish remote ownership. Mount/hide can currently return control to the bot; a private interaction must override that behavior.

Current `bots.pause` prevents future runner dispatch; it does not establish the accepted mid-turn all-tool pause contract. Keep Pause separate from current Stop/interrupt semantics and wire its enforcement through provider and MCP dispatch gates.

## Shared contracts needed before implementation

The files lane and computer lane need the same trusted request context through `server.ts` and `remote-host.ts`: authenticated connection ID, principal kind/device identity and an abort/close lifecycle. It must originate from the accepted connection, never from client-supplied params. Internal daemon dispatch is a distinct principal and must not automatically gain device-only file/browser/vault capabilities.

Proposed browser lease: bind human control to host/bot/generation, current connection ID and a changing control epoch. Only its current owner may send input, resize, navigate or release. Disconnect, revocation, tab/page changes and host switch invalidate pending input and release held keys/buttons. Local native input and remote input share the same arbiter.

Proposed private state: host-owned private epoch plus explicit begin/end operations. Beginning private state invalidates queued bot work and capture operations; enforce the check before execution and before delivering results. Suppress screenshots/thumbnails and page inspection, evaluation, network/console collection and other output channels for the duration. Private state survives panel hiding/control-client disconnect until the owner explicitly resumes or the host closes the session safely. Never auto-resume because a visual overlay unmounted.

Do not route viewer frames or keyboard text through persistent chat/events. Reuse the existing Noise connection and bounded frame messages; validate page/generation/viewport/lease on every input. Drop stale frames instead of queueing an unbounded video backlog.

## Vault decision and test boundary

The accepted plan's enforceable contract is that Tjommie's vault/fill paths do not emit vault secrets into model inputs, tool results, application screenshots during fill, chat/events, logs or diagnostics. It does not promise that an arbitrary receiving site cannot expose a value later.

OS credential storage protects secrets at rest; it is not a complete security boundary from unrestricted processes running as the same Windows user. In particular, Full auto execution requires a separate containment decision before claiming that a bot cannot read OS-protected credentials through some other process. Do not hide this behind an opaque entry ID or a passing mocked-store test.

Use separately namespaced host credential references and metadata records, reusing transport patterns from `packages/daemon/src/account-credentials.ts` rather than API-key validation rules. No existing real credentials may be enumerated/read by development checks. Native fill must accept an opaque entry reference and exact approved HTTPS origin/profile/page generation, not a bot-provided script or selector.

Secret creation/editing needs a trusted dedicated native/isolated input surface; do not place raw values in the ordinary app store. Remote clients request an opaque host operation and do not receive plaintext. Synthetic-store checks can run without touching Windows Credential Manager; disposable real OS-store acceptance is a later explicit check.

Required tests include queued/in-flight capture races, wrong/stale controller, disconnect with held input, panel hiding during private fill, post-navigation origin changes, unexpected frames, and a unique synthetic-secret absence check across every output sink. A successful secret fill alone is insufficient.

## P8 pre-implementation blocker — superseded by the source follow-up below

At this earlier checkpoint no production vault store or fill API was exposed by this lane. OS credential protection does not isolate a secret from unrestricted Full auto processes running as the same Windows user. An opaque entry reference, private browser epoch or mocked credential store cannot fix that boundary. Enabling vault fill under that condition would make the accepted disclosure claim false; the safe result is to remain unavailable until a real process/user isolation boundary and a trusted native secret-entry surface are implemented and verified.

The private-mode foundation and synthetic output checks above are prerequisites only. They are not exact-origin HTTPS vault fill, OS-store acceptance, complete prompt/log/diagnostic sink acceptance, restart safety, physical Android acceptance, or proof against a receiving website re-exposing a submitted value. No owner credentials, installed application/profile, phone, microphone, paid provider, cloud deployment, build, commit or push was used.

The earlier shared-SID/global-WTS design was rejected before enabling the feature. The unelevated host could not obtain a complete cross-user ownership snapshot; provisioning and reboot would not resolve that persistent host-token restriction. A point-in-time snapshot would also not prevent a same-SID Full auto process from changing review policy. The implementation now requires a **fresh separate review-only SID**, its own Windows logon credential and profile/HKCU, and no owner/provider fallback. Both purpose-specific v2 configurations bind the reversed peer SID/root and reject owner/worker/root aliasing. The review scope is selected before resolving account profiles or starting version/acceptance/review work. Ordinary provider/setup/check launches remain on the provider SID. The chosen provider API account/key may still be shared under existing account reservations/budgets; this boundary protects Windows identities, writable profiles and policy, not exclusive ownership of that provider API account.

Each native review job holds an owner/System/Administrators-only global mutex keyed to that review SID, excluding another trusted host or acceptance fixture while the job runs. A protected `CreateNew`/flushed active marker precedes native process creation. Only confirmed job retirement permits marker removal; closed-receipt delivery precedes mutex release. A stale marker or abandoned mutex refuses subsequent reuse, including the case where the last OS mutex handle disappeared. Unconfirmed termination retains the account/scratch reservation and logical ownership marker. This uses the supported [global mutex namespace](https://learn.microsoft.com/en-us/windows/win32/termserv/kernel-object-namespaces), without requiring privileged global process enumeration or running the desktop as administrator. Separate fresh review credentials are never supplied to Full auto, and review SID launches are available only in the trusted tool-free scoped flow.

Directory grants now reject trusted helper/runtime ancestors and descendants, peer roots and canonical actual peer OS profiles. Within the owner root, only assigned `bots/<id>` and `workspaces/<id>` paths are eligible; data/accounts/logs/shared attachments/configuration/receipt paths and hidden worktree metadata are refused, including through aliases. The native grant pins and verifies a canonical directory handle and updates that handle's ACL. Before every readiness/native launch, the helper audits **every** runtime file/directory owner and explicit/inherited ACL, rejects untrusted write/delete/ACL-changing rights and null DACLs, and refuses reparse targets. An owner-only root does not conceal a writable child. The bounded audit permits at most 100,000 nodes/20 seconds; native CLI distributions keep the closure small.

The runnable setup and acceptance artifacts are `scripts/vault/provision-worker.ps1`, `worker-credential.ps1`, `accept-worker.ts` and `README.md`; packaging copies them and the native helper/entry assets. Setup creates two standard accounts and independent owner-stored Windows logon credentials. Both protected acceptance receipts bind purpose, both SIDs and both exact configuration hashes; v1/shared-SID receipts cannot enable the feature. Actual setup requires separately approved account/ACL provisioning, protected runtime installation, shutdown/disabled autostart of older provider hosts, reboot, fresh provider sign-in and successful synthetic denial/version/policy acceptance. Reboot alone is insufficient: readiness also rejects owner-level or untracked worker provider CLIs. Acceptance holds a known synthetic peer file, registry key and native process live while the other SID proves denied peer file read/write, policy-registry modification and process-memory access. It also requires denied synthetic owner file/credential/process/desktop access, permitted own writes, both CLI version commands under both identities and pre/post review policy proof. It never reads an existing owner credential or starts a model turn.

Actual paired-SID provisioning/acceptance remains **unrun**, and Logins remains unavailable until those machine checks pass. Automatic approval review rejected a separate owned temporary native ACL fixture command before execution with `blocked by policy` and no further reason; it was not retried. Therefore the new native handle-ACL and actual OS mutex behavior have compile/source/synthetic evidence, not runtime OS acceptance. The automated helper regressions use only in-memory security descriptors, fake mutex methods and synthetic tree metadata; they do not call native ACL setters or create OS mutexes. ## Windows launch argument transport follow-up — 2026-11-03

Read-only machine-acceptance preparation found that the existing `CreateProcessWithLogonW` invocation exceeded its [documented 1,024-character command-line limit](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createprocesswithlogonw): the fixed denial probe, peer holder and policy observer already needed 3,249, 1,263 and 1,440 characters respectively before variable payloads for the proposed isolated test root. Provisioning and reboot alone could not resolve this defect. No setup was attempted.

The shared launcher now creates a short fixed protected-Node bootstrap for every provider/setup/check/review/observer/acceptance launch. A length-prefixed private stdin frame carries only the target file/argv, followed byte-for-byte by the provider protocol input. The bootstrap inherits cwd, validated environment and stdin/stdout/stderr; no payload file or environment/argv copy is created. Native Windows logon credentials never enter the frame. Target argv uses Windows quoting and the 32,767 UTF-16-unit command-line bound including its terminator; NUL input is rejected early, and Node startup environment variables are removed for bootstrap and target.

The bootstrap remains suspended until SID/token verification and assignment to a protected randomly named Job. Native v3 launch receipts bind purpose/SID/root/Job; candidate processes require pinned live handles and `IsProcessInJob` against the owner-only Job, without trusting PID snapshots or ancestry. Both identities share a preparation gate covering status/acquire and launch. Known receipts remain until successful stopped-proof verification. Only confirmed retirement permits one pre-ack refresh/retry; poisoning during verification, directory/credential waits or receipt preparation prevents another launch/continue and retains any owned child's retirement obligations.
